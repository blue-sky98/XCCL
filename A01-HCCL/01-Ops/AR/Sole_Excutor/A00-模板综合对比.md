## 场景设定与关键公式

> **数据切分场景**：rankSize = **5**（非 2^i），dataType = **u64**（8 字节），dataSize = **34.125 MB**（dataCount = 4,472,832），hcclBuff.size = **4 MB**，HCCL_MIN_SLICE_ALIGN = 128 字节。
>
> **性能对比场景**：rank = 4（ds 能被 4 整除）和 rank = N（N = 2^i，N ≥ 2，ds 能被 N 整除）。

```
maxDataSizePerLoop = min(hcclBuff.size, hcclBuff.size / mult / 128 × 128)
maxDataCountPerLoop = maxDataSizePerLoop / dataTypeSize_
loopTimes = ⌈dataCount_ / maxDataCountPerLoop⌉
```

| 算法结构 | 广播+Reduce | RS+AG | RS+AG | 流水RS+AG | AG+Reduce |

| 线程数 | N | N | 1 | N | 1 |

| 单 rank 通信总量 | 2(N-1)·ds | 4(N-1)/N·ds | 4(N-1)/N·ds | 4(N-1)/N·ds | 2(N-1)·ds |
| LocalCopy 数据量 | 1·ds | 2/N·ds | 2·ds | 2/N·ds | 2·ds |

| Reduce 数据量 | (N-1)·ds | (N-1)/N·ds | 重叠 | 重叠 | (N-1)·ds |
| 通信步数 | 1 (N-1路并行) | 2 (各N-1路并行) | 2log₂N (串行) | (N-1)+1 (流水) | log₂N (串行) |
| 通信并行度 | N-1路 | N-1路 | 1路 | N-1路 | 1路 |

> **N-rank 通式说明**：
> - **OneShot / AicpuReduceNHR**：全量收发，通信总量 = 2(N-1)·ds，随 N 线性增长；cclBuff = N×ds，内存随 N 线性增长。
> - **TwoShot / NHR / MeshChunk**：RS+AG 架构，通信总量 = 4(N-1)/N·ds，当 N→∞ 时趋近 4·ds（收敛）。
> - **NHR / AicpuReduceNHR**：单线程零同步，通信步数 O(log₂N)，但串行执行无并行度。
> - **MeshChunk**：同步次数 = 2N，随 N 线性增长；流水线步数 = N-1，可掩盖延迟但同步开销最重。

## 4. Reduce 方式对比

| 模板 | Reduce 位置 | Reduce 接口 | Reduce 时机 | 特殊数据类型支持 |
| --- | --- | --- | --- | --- |
| OneShot | 通信后 | `LocalReduce` | 所有通信完成后 | ✓ 支持 |
| TwoShot | Scatter 后 | `LocalReduce` | Scatter 完成后 | ✓ 支持 |
| NHR | 通信内联 | `SendRecvBatchWriteReduce` | 每步通信中实时 | ✗ 不支持（DMA限制） |
| MeshChunk | 通信内联 | `SendRecvBatchWriteReduce` | 每步通信中实时 | ✗ 不支持（DMA限制） |
| AicpuReduceNHR | AG 后 | `LocalReduce` | AllGather 完成后 | ✓ 专为支持 |

> **内联归约 vs 分离归约**：
> - **通信内联归约**（NHR, MeshChunk）：归约与通信重叠，无额外遍历，但不支持特殊数据类型（DMA 限制）。
> - **分离 LocalReduce**（OneShot, TwoShot, AicpuReduceNHR）：支持所有数据类型（AICPU 执行），但归约在通信后单独执行，有额外开销。

## 6. 算法选择逻辑

```
SelectAicpuAlgo
├── 特殊数据类型 (int64/uint64/fp64/PROD)  →  InsAllReduceAicpuReduceNHR
├── 单级 UBX + meshNum == closNum + rank ≤ MAX
│   ├── dataSize ≤ SMALL_DATA_SIZE          →  InsAllReduceMesh1DOneShot
│   └── else                                →  InsAllReduceMesh1DTwoShot / MeshChunk

```

> **u64 场景**：对于 u64 数据类型，实际可用的模板为 OneShot / TwoShot / AicpuReduceNHR。选择器会将 u64 路由到 **AicpuReduceNHR**。NHR / MeshChunk 因 DMA 内联归约限制不适用。

## 7. 关键差异根源分析

### 7.1 cclBuff 倍率差异根源

| 倍率 | 模板 | 根源 |
| --- | --- | --- |
| N× | OneShot, AicpuReduceNHR | 需存储 N 份完整副本（每份 = dataSize），供全量 Reduce |
| 2× | TwoShot, MeshChunk | 需存储 N 份 slice 副本，非均衡切分时 N×ceil(count/N) > dataSize |
| 1× | NHR | 连续分区 + 通信内联归约，无需存储 N 份副本 |

### 7.2 通信量差异根源

| 通信量 | 模板 | 根源 |
| --- | --- | --- |
| 2(N-1)·ds | OneShot, AicpuReduceNHR | 全量广播/全量收集，每对交换完整 dataSize |
| 4(N-1)/N·ds | TwoShot, NHR, MeshChunk | ReduceScatter + AllGather，每对仅交换 dataSize/N |

### 7.3 并行度 vs 同步开销权衡

```
高并行 + 高同步                          低并行 + 零同步
    ←─────────────────────────────────────────────→
    MeshChunk(2N同步, N-1路并行) → TwoShot(4同步, N-1路) → OneShot(2同步, N-1路) → NHR/AicpuReduceNHR(0同步, 1路)
```

> - **Mesh 系**（OneShot/TwoShot/MeshChunk）：多线程并行通信，但有同步开销；适合单级 Mesh 全互连拓扑。
> - **NHR 系**（NHR/AicpuReduceNHR）：单线程串行通信，零同步；适合任意拓扑、通用兜底。

## 8. 为什么 Two-Shot 的 CCL Buffer 需要 2 × dataSize？

> **源码注释**（`ins_temp_all_reduce_mesh_1D_two_shot.cc:24`）：
> `multiple=1且数据非均衡切分时，hcclBuffer会不足，因此用2`

根本原因：`ScatterData` 阶段对 cclBuff 的"按本 rank 切片大小等距划槽"布局，叠加 `SplitData` 的"向上取整"切分策略，在非均衡切分时产生**放大效应**，使实际占用超过 1× dataSize。

### 8.1 cclBuff 布局——N 个等大槽位

本 rank 的 cclBuff 被划分为 N 个连续槽位，**每个槽位大小都等于本 rank 负责切片的大小** `recvSize = sliceInfoList_.at(myRankIdx_).size`：

```
cclBuff: |  slot0  |  slot1  | ... |  slotN-1  |
      offset: 0      recvSize    2×recvSize     (N-1)×recvSize
      每槽大小: recvSize（等大）
```

> **关键代码**：
> - `:199` `recvSize = sliceInfoList_.at(myRankIdx_).size`
> - `:216` 本地拷贝目的偏移：`hcclBuffBaseOffset + remoteIdx * recvSize`
> - `:236` 远端接收目的偏移：`hcclBuffBaseOffset + remoteIdx * recvSize`
>
> Scatter 阶段共需 **N × recvSize** 字节，是 cclBuff 占用的瓶颈。

### 8.2 切分策略——向上取整导致 N × ceil(count/N) > count

`SplitData:129-160`：每个切片元素数 `sliceCount = RoundUp(count_, N) = ceil(count/N)`，仅末尾切片可能更小。因此对于非末尾 rank：`recvSize = ceil(count/N) × dataTypeSize`。

```
当 count % N ≠ 0 时：N × ceil(count/N) > count → N × recvSize > dataSize
```

### 8.3 放大比量化

| count | N | ceil(count/N) | N×ceil(count/N) | 放大比 | 1× 够吗 | 2× 够吗 |
| --- | --- | --- | --- | --- | --- | --- |
| 1000 | 4 | 250 | 1000 | 1.000× | ✓ | ✓ |
| 1001 | 4 | 251 | 1004 | 1.003× | ✗ | ✓ |
| 5 | 4 | 2 | 8 | 1.600× | ✗ | ✓ |
| 1 | 4 | 1 | 4 | 4.000× | ✗ | ✗ |

> - **均衡切分**（count 能被 N 整除）：放大比 = 1，1× 即可，2× 冗余。
> - **非均衡切分且 count ≥ N**：放大比上限 = `2N/(N+1) < 2`，**2× 恰好覆盖**。
> - **count < N 极端小数据**：放大比可超过 2，但 Two-Shot 面向大数据，不在主要设计考量内。

### 8.4 结论

> `multiple = 2` 是针对"非均衡切分 + count ≥ N"这一常见场景的安全倍率：1 倍会因向上取整放大而不足；2 倍恰好覆盖全部情况。
>
> **One-Shot 不受影响**：其 cclBuff 槽位存完整 dataSize 副本，N 个槽位 = N × dataSize，与倍率 N 严格匹配。

## 9. 为什么 MeshChunk multiple=1 时 hcclBuffer 会不足

### 9.1 代码表面分析：偏移计算本身不溢出

所有偏移都是按**实际数据大小**累加的，理论上 1 × dataSize 足够：

```
一级切分：sliceInfoVec[rank][0].offset 按 currChunkSize 逐段累加，总累加 = dataSize
二级切分：sliceRxOffset_ / sliceTxOffset_ 循环累加 sliceSize[rank][m]，合计 = chunk 实际大小
写入地址：cclBuffBaseOff + sliceInfoVec[myAlgRank_][0].offset + sliceRxOffset_
```

**数值验证**（N=4, count=9, dataTypeSize=4B, dataSize=36B）：

| rank | chunk offset | currChunkSize | 二级 sub-slice | 结束偏移 |
| --- | --- | --- | --- | --- |
| 0 | 0 | 12B | [4B, 4B, 4B] | 12B |
| 1 | 12 | 12B | [4B, 4B, 4B] | 24B |
| 2 | 24 | 12B | [4B, 4B, 4B] | 36B |
| 3 | 36 | 0B | [0, 0, 0] | 36B |

> 最大结束偏移 = 36B = dataSize，**不溢出**。

### 9.2 深层原因：标称槽位大小 vs 实际数据大小

"不足"根源在于 **cclBuffer 的槽位布局按标称 chunkSize 规划，而非按实际 currChunkSize**。

```
标称槽位模型：
    chunkSize = RoundUp(count, N) × dataTypeSize（对齐后的标称大小）
    每个 rank 的 chunk 槽位统一按 chunkSize 预留（N 个等大槽位）
    标称总空间 = N × chunkSize

实际数据模型：
    前 N-1 个 chunk 实际大小 = chunkSize
    最后 1 个 chunk 实际大小 = dataSize - (N-1) × chunkSize ≤ chunkSize
    实际总数据 = dataSize
```

```
当 count % N ≠ 0 时：
    N × chunkSize = N × ceil(count/N) × dataTypeSize > N × (count/N) × dataTypeSize = dataSize
    即：标称总槽位 > 实际数据总量
```

### 9.3 为什么需要按标称槽位规划

**1. DMA / 通信接口的统一配置**
SendRecvBatchWriteReduce 写入对端 remote cclBuffer；通信链路的内存注册（remoteCclMem）通常按统一块大小配置描述符；若每个槽位大小不同，DMA 地址映射和边界检查会非常复杂。

**2. 地址计算的简洁性与健壮性**
按等大槽位：rank k 的 chunk 起始地址 = `base + k × chunkSize`；无需查表即可计算任意 rank 的 chunk 位置，简化流水线调度逻辑。

**3. 二级 sub-slice 的对齐访问**
每个 chunk 内部的 sub-slice 索引按标称位置计算；大块/小块混合时，按最大可能的 sub-slice 大小预留槽位更安全。

### 9.4 数值对比：标称 vs 实际

**例 1：非均衡切分**（N=4, count=9, dataSize=36B，chunkSize=12B）

| 维度 | 计算公式 | 大小 |
| --- | --- | --- |
| 标称总槽位 | N × chunkSize = 4 × 12B | **48B** |
| 实际数据量 | dataSize | 36B |
| 差值 | 48 - 36 | **12B（溢出 33%）** |

> multiple=1 → cclBuffer=36B **<** 48B → **不足**

**例 2：均衡切分**（N=4, count=8, dataSize=32B，chunkSize=8B）

| 维度 | 计算公式 | 大小 |
| --- | --- | --- |
| 标称总槽位 | N × chunkSize = 4 × 8B | 32B |
| 实际数据量 | dataSize | 32B |
| 差值 | 32 - 32 | **0B（刚好）** |

> 均衡时 multiple=1 → cclBuffer=32B = 32B → **刚好够用**。
>
> 这就解释了注释的精确表述："**数据非均衡切分时**，hcclBuffer 会不足"——均衡时 1 倍确实够，非均衡时标称槽位膨胀导致不足。

## 10. NHR 收发信息（GetReduceScatterStepInfoList / GetAllGatherStepInfoList）

### 10.1 NHRStepInfo 结构体

```
struct NHRStepInfo {
    u32 step = 0;        // 当前步数
    u32 myRank = 0;      // 本 rank 索引
    u32 nSlices;        // 本步交换的 slice 数量
    u32 toRank = 0;      // 发送目标 rank
    u32 fromRank = 0;    // 接收来源 rank
    std::vector txSliceIdxs;  // 发送的 slice 索引列表
    std::vector rxSliceIdxs;  // 接收的 slice 索引列表
};
```

### 10.2 ReduceScatter 每步通信信息

`GetReduceScatterStepInfoList`：对于 RS，rank 间间隔逐渐增大，nSlices 逐渐减小。

```
for (u32 step = 0; step < nSteps; step++) {
    // 计算通信对象
    u32 deltaRank = 1 << step;            // 步长：1, 2, 4, ...
    u32 sendToIdx = (myRankIdx_ + N - deltaRank) % N;  // 发送目标
    u32 recvFromIdx = (myRankIdx_ + deltaRank) % N;    // 接收来源
    // 数据份数
    u32 nSlices = (N - 1 + (1 << step)) / (1 << (step + 1));
}
```

### 10.3 AllGather 每步通信信息

对于 AG，rank 间间隔逐渐减小，nSlices 逐渐增大（与 RS 对称）。

```
for (u32 step = 0; step < nSteps; step++) {
    u32 deltaRank = 1 << (nSteps - 1 - step);  // 步长递减：2^(nSteps-1), ..., 2, 1
    u32 sendToIdx = (myRankIdx_ + deltaRank) % N;
    u32 recvFromIdx = (myRankIdx_ + N - deltaRank) % N;
    u32 nSlices = (N - 1 + (1 << (nSteps - 1 - step))) / (1 << (nSteps - step));
}
```

### 10.4 N=5 示例（myRankIdx=1）

| 阶段 | step | deltaRank | toRank | fromRank | nSlices | txSliceIdxs | rxSliceIdxs |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **RS** | 0 | 1 | 0 | 2 | 2 | [0, 3] | [1, 4] |
| | 1 | 2 | 4 | 3 | 1 | [4] | [1] |
| | 2 | 4 | 2 | 0 | 1 | [2] | [1] |
| **AG** | 0 | 4 | 2 | 0 | 1 | [1] | [2] |
| | 1 | 2 | 4 | 3 | 1 | [1] | [4] |
| | 2 | 1 | 0 | 2 | 2 | [1, 4] | [0, 3] |

> **RS 与 AG 对称**：AG 的 deltaRank 顺序与 RS 相反（4→2→1），toRank/fromRank 互换，nSlices 递增。RS 负责归约分散，AG 负责收集广播，二者共同完成 AllReduce。
